# 保健品按「产品」同构建模，不单列实体

CLAUDE.md 把保健品（褪黑素、圣约翰草等）纳入产品范围，但领域模型里它一度没有干净的家——`interaction.yaml` 把圣约翰草当成一个「成分」硬塞进了 drugs 表。我们决定：**保健品与 OTC 药品统一为同一个概念「产品 (Product)」**，按商品名入同一张主数据表、同样拆成分、同样参与叠加与相互作用检查；保健品只是 `approval_number` 为空、`otc_category` 标记为「保健品」的产品。

保健品真正不同于药品之处——说明书更含糊、相互作用证据更弱——**已经由两个正交的既有字段承载**：`ingredients_verified`（保健品通常为 false）与规则的 `confidence`（铁律 #4 要求保健品规则标 medium / low）。再引入一个 `Supplement` 实体类型，等于把同一信息编码第二遍，还会逼着叠加 / 相互作用引擎在一组异构集合上各跑一遍。

## Considered Options

- **当作「物质 Substance」**：否决。物质没有商品名与说明书，而保健品是有 mg 含量的片剂；如此建模会同时丢掉叠加计算（需按成分含量求和）与引用（铁律 #2 要求用药回答必带说明书原文），违反两条铁律。
- **独立第三类实体 Supplement**：否决。语义最纯，但真正的差异已被上述正交字段覆盖，独立类型只带来重复的入库管线与跨异构集合的检查逻辑，属投机性拆分（YAGNI）。

## Consequences

- 代码里的 `Drug` / `drugs` 从此是「产品」的历史命名；是否改名为 Product 属可选重构，不阻塞功能。
- 若将来保健品出现真正专属的规则（如独立的引用 / 免责标准），可再行拆分——届时需迁移已入库的保健品数据，这正是本决定不算「轻易可逆」之处。
